# 微信读书打卡（dsh-weread-checkin）

在 DeepSeek Harness 里完成微信读书每日打卡：手动一键、每天定时、或让 AI 代劳。

## 原理

微信读书**没有独立的「打卡」接口**。服务端把「当日有效阅读时长 ≥ 5 分钟」自动记为一个打卡天，
所以本插件通过 `POST https://weread.qq.com/web/book/read` 每 30 秒上报一次阅读时长来实现打卡。
读书小队积分同样由阅读时长驱动，因此也会被一并累积。

> 接口与签名算法逐字对照 [findmover/wxread](https://github.com/findmover/wxread) 的
> `main.py` / `config.py` 实现，并用 6 组用例与 Python 源码逐例比对，结果完全一致。

## 两个概念，别混

| | 每日目标 | 打卡时长 |
|---|---|---|
| 作用 | 判定「今天算不算打卡成功」 | 一次点击最多补多少分钟 |
| 影响 | 进度条、日历颜色、侧边栏圆点 | 单次跑多久、自动打卡跑多久 |
| 档位 | 5 / 10 / 15 / 20 / 30 / 45 / 60 分钟 | 5 / 10 / 15 / 20 / 30 / 45 / 60 分钟 |

点「立即打卡」是**补差额**：今天已读 3 分钟、目标是 10 分钟，就只跑 7 分钟，凑满即停。
已经达标时按钮直接变成「今日已达标」，不会重复上报。

## 界面

**左侧栏的书本图标带一个三色状态点**，一眼看出今天的情况：

| 颜色 | 含义 |
|---|---|
| 绿 | 今日阅读已达「每日目标」 |
| 黄 | 今天还没打满（未达成目标） |
| 红 | Cookie 失效 / 未配置 / 最近一次运行报错 |

> 红点是真·登录态探测的结果：插件会实际请求一次 `/web/shelf/sync`。
> 否则 Cookie 过期时官方 API Key 通道照样返回漂亮统计，就成了「假绿」。

点图标打开面板，iOS 风格的分组卡片依次是：

- **今日** —— 大号当前时长 / 目标、进度条（按每日目标推进，达成变绿）、一键「立即打卡」
  - 打卡进行中：按钮变灰显示 `打卡中 6/20`，带转圈，不可点击
  - 进度条实时前进：每 30 秒刷新一次，不用手动刷
- **打卡设置** —— 每日目标、打卡时长、自动打卡时间
- **打卡日历** —— 周 / 月可切换，**一周从周一开头**
  - 周视图：一周七格，带 ‹ › 翻周
  - 月视图：月历，可翻到 2026 年 1 月为止的历史
  - 达标绿色（按超出目标的多少分 4 档深浅）、未达标红色（按完成度分 3 档）
- **我的书架** —— 默认展开，显示两排封面（点「全部 N 本」展开全部）；每本书下方是今年阅读时长，按今年时长排序
- **累计** —— 总阅读时长、有效阅读天数、读过 / 读完 / 笔记数

**取数时机**（省流量也省接口）：

| 场景 | 行为 |
|---|---|
| 打开面板 | 拉一次最新数据（含书架，因为它默认展开） |
| 打卡进行中 | 每 30 秒刷新一次进度 |
| 切到日历「月」视图 | 此时才请求 2026-01-01 起的历史 |
| 展开 / 收起书架 | 收起后不再重复请求，命中本地缓存 |
| 空闲 | 不轮询（只有侧边栏圆点每 2 分钟探一次登录态） |

## 配置

在界面里粘贴即可，**不用手动编辑任何文件，也不需要抓包**。
打开 **设置 → 插件 → 微信读书打卡**：

### ① Cookie（必需）

1. 浏览器打开 https://weread.qq.com/ 并确认已登录
2. F12 → Network → 过滤 `read` → 点 `https://weread.qq.com/web/book/read`
3. 右键 → **Copy → Copy as cURL (bash)**
4. 整段 cURL 粘进 Cookie 框 → 保存（只粘 Cookie 字符串也行，插件两种都能解析）

### ② 请求体模板（可选，留空即用内置模板）

上报接口的 `b`（书籍）、`c`（章节哈希）、`ps`/`pc`（用户与设备标识）理论上需要是同一次
真实阅读产生的配对。但实测服务端**不逐字段校验**——只要这组值曾经真实产生过就能通过：

```
内置模板 → 上报 → 官方统计今日 1197 → 1230 秒（+33，正好等于两次 rt 之和）
```

所以内置了一份实测可用的模板作为兜底，**普通用户完全不用抓包**。
只有当内置模板日后失效时，才需要按上面的步骤把 `/web/book/read` 的请求体粘进第二个框覆盖它。

### ③ 官方 API Key（可选，但强烈建议）

形如 `wrk-xxxxx`，从微信读书官方 skills 处获取。配上它之后才能**验证**打卡是否真的计入时长，
日历、书架、累计统计也都依赖它。

凭据保存在本机的 `C:\Users\<你>\.dsh\weread-credentials.json`，不写进插件配置。

> Windows 上如果把 Key 写在「用户环境变量」里，已经在运行的 Host 进程读不到
> （进程环境在启动时固定），所以请在设置页里也填一份。

## 验证打卡是否真的生效

**只看 `{"succ":1}` 是不够的**——请求被接受不等于时长已累加。插件的做法是：

```
打卡前读官方 /readdata/detail 的「今日」秒数
  → 执行上报
  → 再读一次，比对增量
```

面板打卡成功后直接显示「打卡生效：今日阅读 +N 秒」；没涨就明确报错，不会假装成功。

## 使用方式

| 方式 | 说明 |
|---|---|
| 左侧栏面板 | 点书本图标 → 「立即打卡」，实时显示时长是否增长 |
| 插件设置页 | 粘贴 Cookie / 模板 / API Key、刷新密钥 |
| `/weread` | 在输入框执行，`/weread 30` 可指定分钟数（会覆盖补差额逻辑） |
| 对话 | 对 AI 说「帮我微信读书打卡」（工具 `weread_checkin`） |
| 自动 | 面板里设时间（如 `08:30`），每天该时刻自动跑一次 |

五者共用同一份实现。自动打卡由插件内置定时器驱动，**不会出现在「自动化任务」界面，
也不消耗对话 token**，代价是那一刻 DSH 需要在运行。

> 定时器有补跑语义：到点后如果 DSH 没开，下次启动后仍会补上（一天最多补 3 次）。

## 配置项（`cordis.patch.yml`）

| 字段 | 默认 | 说明 |
|---|---|---|
| `minutes` | `10` | 默认打卡时长（分钟）；面板里改过就以面板为准 |
| `goalMinutes` | `10` | 默认每日目标；面板里改过就以面板为准 |
| `autoTime` | `""` | 每天自动打卡的本地时间，`HH:MM`；留空则禁用 |

## 数据来源与已知边界

| 数据 | 来源 | 边界 |
|---|---|---|
| 每日时长 | `/readdata/detail` 的 `mode=monthly` + `baseTime` 逐月拉 | 年度模式不返回日级桶，所以历史要按 11 个月各拉一次（约 2.4 秒） |
| 每本书时长 | 各月 `readLongest` 取并集 | 只给 top10 且过滤 5 分钟以下，所以书架里如实标注「时长覆盖 N/M 本」 |
| `/book/getprogress` | 有 `recordReadingTime` 字段 | 实测 27 本全是 0，**不可用**，故未采用 |

## 注意事项

- `wr_skey` 有效期约 90 分钟，插件会在鉴权失效（-2012/-2013）时自动调
  `/web/login/renewal` 续期；整体登录态约 30 天，过期需重新粘贴 Cookie
- 不要在别的浏览器重新扫码登录，会使当前 Cookie 提前失效
- 计时以「当日阅读统计」为准，不是单本书的 `readingTime`
- 仅供学习研究，存在账号风险，请自行评估
